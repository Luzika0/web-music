# K-Song

K-Song is a responsive Angular music discovery and streaming application. It includes a home page, music search, artist directory, discovery, account-backed library and liked songs, account registration and verification, sign-in and password reset, HLS playback, and a permission-gated creator studio.

The interface supports dark and light themes built around the two brand base colors: `#000040` for dark mode and `#ebebed` for light mode, with the opposite color used for contrast. Inter, Battambang, and Noto Sans Khmer are bundled locally. Khmer text prefers the locally installed Khmer OS Battambang face when available, then uses bundled Battambang and Noto Sans Khmer. Khmer text receives `lang="km"` metadata, normal letter spacing, and Khmer-friendly line height for correct shaping and readable marks. Use the sun/moon control in the top navigation to switch appearance; K-Song remembers the choice in the current browser. Interactive navigation, search, theme, favorite, and playback icons have subtle motion and honor reduced-motion preferences.

Selecting a song opens the dedicated `/now-playing` listening room. In Discover, the track number, cover art, and metadata area form one large keyboard-accessible play target; the favorite and explicit play controls remain separate. The listening room shares the persistent app audio player, so playback continues while navigating. Its queue follows the currently displayed song list from Discover, Search, Home, or Liked Songs; select any queued track or use Previous/Next, and playback advances automatically at the end of a track.

## Requirements and setup

- Node.js compatible with Angular 22 and npm.
- The K-Song API service. Set its origin in `.env` before running the browser app.

```powershell
npm install
Copy-Item .env.example .env
# Edit .env and set KSONG_API_BASE_URL to the API origin.
npm start
```

Open `http://localhost:4200`. `npm run build` creates the production build, and `npm test` runs the unit tests. The npm start/build/watch/test scripts generate the browser runtime config from `.env` and shell environment variables; the generated `public/ksong-config.js` is ignored by git. If both are set, process environment values take precedence.

## Configuration

| Variable | Default | Description |
| --- | --- | --- |
| `KSONG_API_BASE_URL` | empty (same origin) | API origin, such as `https://api.example.test`; do not include a trailing slash. |
| `KSONG_BACKGROUND_COLOR` | `#000040` | Main page background color. |
| `KSONG_ACCENT_COLOR` | `#ebebed` | Prominent button/control color. |
| `KSONG_PAGE_SIZE` | `8` | Number of artists and songs requested per discovery page (integer from 1 to 100). |
| `KSONG_REFRESH_BUFFER_SECONDS` | `60` | Refresh access tokens this many seconds before expiry (integer from 0 to 3600). |

Copy `.env.example` to `.env`. These values are public browser configuration, not secrets. Do not put credentials, tokens, or private keys in this file.
Runtime configuration is generated by `scripts/prepare-config.mjs` for npm start/build/test/watch. Shell environment variables override `.env`; invalid numeric settings fall back to their documented defaults. Changes to `.env` are picked up the next time an npm script runs.

## Project structure

- `src/app/` — application shell (`app.ts`, `app.html`), top-level routes, and Angular providers.
- `src/app/core/` — singleton services, runtime configuration, authentication adapter, and route guards.
- `src/app/core/services/music-api.service.ts` — typed API boundary, response normalization, session, refresh, and playback requests.
- `src/app/core/services/playback.service.ts` — playback token and HLS session state.
- `src/app/core/guards/admin.guard.ts` — client-side navigation guard; backend authorization remains authoritative.
- `src/app/features/discover/` — public artist search, song discovery, pagination, and player actions.
- `src/app/features/player/` — dedicated now-playing page and shared player controls.
- `src/app/features/home/` — home landing page with current catalog highlights.
- `src/app/features/search/` — song and artist search through the existing catalog routes.
- `src/app/features/artists/` — paginated artist directory and search.
- `src/app/features/library/` — account-backed liked tracks and editable playlists with real catalog song metadata.
- `src/app/features/auth/` — registration, OTP verification, login, and password-reset flows.
- `src/app/features/admin/` — artist/song uploads and song deletion, using the existing backend routes.
- `src/app/core/services/library.service.ts` — account-backed favorites and playlists through `/api/auth/library/**`.
- `src/app/core/services/media-cache.service.ts` — browser SQLite catalog and artwork cache persisted as a SQLite snapshot in IndexedDB.
- `src/app/shared/components/` — reusable UI components, including authenticated media artwork.
- `src/app/app.spec.ts` — app, API integration, and runtime-configuration tests.
- `src/styles.scss` — global design tokens and shared responsive styles.
- `scripts/prepare-config.mjs` — maps build/development environment variables to browser runtime configuration.

Feature routes use standalone lazy-loaded components. Keep cross-feature singleton state and API access in `core`, feature-specific screens in their feature folder, and reusable UI in `shared`.

## API assumptions and details to confirm

- The API base URL is configurable; `.env.example` points to the supplied hosted auth-service gateway. The browser origin must be included in the auth-service `app.cors.allowed-origins` setting (Spring environment form: `APP_CORS_ALLOWED_ORIGINS`), and the gateway must be reachable by the browser. The hosted gateway currently returns CORS-blocked/403 responses from `http://localhost:4200` during browser requests. The auth service is stateless, its CORS config disallows credentialed cookies, and login returns token values to browser JavaScript, so K-Song omits cookies and stores `acessToken`, user ID, and `refreshToken` in `sessionStorage` (cleared when the tab session ends). This is exposed to same-origin script execution; a future HttpOnly-cookie/BFF design would require backend response, CORS, and refresh-route changes.
- `auth_service` wraps authentication results in `{ statusCode, message, data }`. Login places the token object at `data.token` with `permission`, `userId`, `acessToken` (spelling preserved), and `refreshToken`; refresh returns `data.newAcessToken`. The access JWT contains an `exp` claim, `type: ACCESS`, a numeric user ID, and the permission claim, so the client schedules refresh before `exp` and uses the separately returned permission only to decide whether to show admin UI. Client-side token parsing or permission checks are never authorization. The refresh route puts `refreshToken` in its query string, which can expose it to API/proxy access logs; a secure `HttpOnly` cookie or non-URL refresh contract is needed to eliminate exposure, and operators must not log refresh query values. See [AuthServiceImpl](https://github.com/Luzika0/auth_service/blob/main/src/main/java/cam_sound/auth_service/service/serviceImpl/AuthServiceImpl.java), [LogInResponse](https://github.com/Luzika0/auth_service/blob/main/src/main/java/cam_sound/auth_service/dto/response/LogInResponse.java), and [JwtService](https://github.com/Luzika0/auth_service/blob/main/src/main/java/cam_sound/auth_service/service/jwt/JwtService.java).
- Permission mapping is isolated in `AdminPermissionAdapter` and fails closed. It reads `data.token.permission` and matches the backend's exact `PERMISSION_ADMIN = "ADMIN"` value; the older `data.permissions` array shape remains accepted for compatibility. The Admin navigation item appears for accounts whose login response supplies that permission. Backend `@PreAuthorize` checks and the music service's `SongServiceImpl.requireAdmin()` remain the real authorization barriers; the frontend route guard is only a navigation/UX check. The gateway must strip any client-supplied identity headers and set trusted `X-User-Id` from the validated bearer token. See [SongServiceImpl](https://github.com/Luzika0/musice-service/blob/main/src/main/java/user/music_service/service/impl/SongServiceImpl.java) and [RequestHeaderInterceptor](https://github.com/Luzika0/musice-service/blob/main/src/main/java/user/music_service/dto/request/RequestHeaderInterceptor.java).
- The music service wraps results in `{ statusCode, message, data }`. Artist pages return `data.totalPage`, `data.totalElement`, and `data.content` with `artistId`, `artistName`, `albumName`, `artistImage`, and `albumImage`. Songs are returned as entities in `data.content` with `songId`, `artistId`, `songName`, `songImage`, and `songType`; the song object does not contain an artist name, so the UI matches artist IDs against artists already browsed and otherwise clearly leaves the name unavailable. The actual `list-song` controller requires a `searchText` query parameter despite the Postman sample's omission; K-Song sends an empty value to list without filtering. Pagination consumes `totalPage`. See [MediaController](https://github.com/Luzika0/musice-service/blob/main/src/main/java/user/music_service/controller/MediaController.java), [Song](https://github.com/Luzika0/musice-service/blob/main/src/main/java/user/music_service/model/Song.java), and [GaneralPagination](https://github.com/Luzika0/musice-service/blob/main/src/main/java/user/music_service/dto/response/GaneralPagination.java).
- The `list-song` route is not included in the auth service's permit-all rules, so it requires a bearer token; artist listing is explicitly permitted. The supplied hosted deployment returned 403 for song listing and did not consistently permit artist listing. K-Song does not bypass this backend access control.
- The Search page sends its term as `searchText` to the existing song-list and artist-list routes; it does not add a backend endpoint. Search results and playback remain subject to the backend's auth/CORS policies. Library favorites and playlists use the Music Service `/library/**` API and are scoped to the authenticated user. Playlist detail responses include ordered song IDs plus safe song metadata; private HLS object keys are never returned.
- Image responses are private R2 streams: the service checks `X-User-Id` and only serves allowed image-key prefixes. K-Song fetches artwork through the shared API client with bearer and user-ID headers, then uses a temporary object URL; signed-out listeners see a designed fallback rather than a broken image. See [MediaController](https://github.com/Luzika0/musice-service/blob/main/src/main/java/user/music_service/controller/MediaController.java).
- Browser media caching uses SQLite (`sql.js`) with the SQLite database snapshot persisted in IndexedDB; Angular serves the SQLite WASM runtime from `assets/sql`. Song and artist catalog pages are available from the cache only when the API cannot be reached, never for authorization or other API errors. Private artwork is still fetched from the API first on each request, so cached bytes do not bypass the backend's authorization check; only a network-level failure can use a cached image for the currently authenticated user. Artwork is stored as SQLite BLOBs, limited to 5 MiB per image and approximately 48 MiB per user, with oldest images pruned first. Catalog entries older than 30 days are removed. A logout clears that user's media cache. The cache is a performance/offline aid, not a backup; if IndexedDB or the SQLite WASM runtime is unavailable, the app displays a notice and continues online without caching. Favorites and playlists are persisted by the Music Service and synchronize across devices.
- The current music-service playback controller prefers `POST /api/auth/song/:songId/playback-token`; its wrapped response is `data.token`, `data.sessionId`, `data.expiresAt`, and `data.songId`. The legacy `GET /playback-token` remains but is not used because creating a session revokes the previous session for that user. Status is `{"active": boolean}` and events are Server-Sent Events, including `playback_taken_over`; K-Song requests the session before streaming, checks status, watches takeover events, and pauses/destroys playback when replaced. HLS assets are streamed at `/song/:songId/hls/:assetName`; the player sends `playBack-token`, bearer, and `X-User-Id` headers. See [SongController](https://github.com/Luzika0/musice-service/blob/main/src/main/java/user/music_service/controller/SongController.java) and [cross-device playback notes](https://github.com/Luzika0/musice-service/blob/main/docs/cross-device-playback.md).
- Artist creation preserves the API multipart spelling `albumIamge` (the Java DTO confirms this typo). Song uploads use `artistId`, `songName`, `songType`, `file`, and `songImage`; `songType` must be one of `ROCK`, `CLASSICAL`, `POP`, `JAZZ`, `HIP_HOP`, `COUNTRY`, or `OTHER`. The user-facing delete route follows the requested `DELETE /api/auth/admin/delete-song/:songId` path with no body. However, the current music-service controller declares `@DeleteMapping("/delete-song")` while requiring a path variable, so that endpoint needs a backend mapping fix to `@DeleteMapping("/delete-song/{songId}")`. Creator Studio lists songs from the authenticated song catalog and supports deletion by selecting a real song record; the ID field remains as a manual fallback. See [AdminSongController](https://github.com/Luzika0/musice-service/blob/main/src/main/java/user/music_service/controller/AdminSongController.java), [ArtistRequest](https://github.com/Luzika0/musice-service/blob/main/src/main/java/user/music_service/dto/request/ArtistRequest.java), and [SongRequest](https://github.com/Luzika0/musice-service/blob/main/src/main/java/user/music_service/dto/request/SongRequest.java).
- Registration dates are submitted as `YYYY-MM-DD`; OTP verification sends `otp`, password reset sends `otpCode`. Confirm the API's OTP length, delivery, and expiration contract.

## Security

The UI only exposes creator tools when the permission adapter grants access, and `/admin` has a route guard. These are usability measures, not authorization. The API must authenticate and authorize each admin and playback operation, validate upload content and size, protect token refresh and cookie flows against CSRF as applicable, and use HTTPS in production.
